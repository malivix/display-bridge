# Current UI audit and feature decisions

Reviewed on 2026-09-21 against source `3d94e42` plus the existing, uncommitted
portrait/preset demo fixture correction in `native/menu/MenuApp.swift`. Current-run
captures use the isolated Preset Comparison Review app. This is a source/demo audit,
not an installed-release audit or a fresh hardware qualification. No hardware command,
sound, notification, clipboard copy, installation or monitor setting change was made.

## Evidence and scope

The goal is to understand the two-monitor state, choose readable sizes and recover
without Terminal, at a text size useful to someone with reduced vision. Captures use
dark appearance and Largest text (24 points); the main window is 600 × 480. The size
and percentage dialogs retain their own dimensions. The synthetic scenario row uses
extra space and does not exist in production. Scrolling is expected at large text;
being below the viewport is a discoverability issue, not proof that content is lost.

The nine screenshots and an illustrated HTML report are private in the ignored
`.local-only/ui-feature-audit-current/` folder. They contain synthetic app state.
Screenshots were captured through the native UI adapter and inspected; the key size,
audio and recovery captures were also reopened from disk. No external upload occurred.

## Prioritized findings

### U1 — Put the decision before technical detail (high)

Step 1 spends most of its initial space on a ratio, explanation and PG dimensions;
the second monitor is below the viewport. `SizeChooser.swift:sizeComparison` emits a
single long text report, with framebuffer lines mixed into each monitor section.
The separate “Preview size” and “Compare readability” entries require the user to
understand the internal tools before finishing one task.

Next change: one compact summary showing both monitor names, current/proposed logical
size and larger/smaller/unchanged result; then Preview. Put framebuffer details and
unavailable presets in accessible expandable sections. Use “PG is about 54% larger”
alongside or instead of “154% of BenQ”, retaining the approximation disclaimer. Keep
qualified candidates, reference filters, identity/orientation binding and Keep/Revert.
Saving an already accepted pair does not need a second calibration database.

Acceptance: both monitor effects and the primary action are visible at Largest in the
minimum chooser; keyboard can expand technical detail; unknown values never look
measured; selected presets retain their estimate; context loss still requires reopening.

### U2 — Make Overview answer the everyday question (medium)

Step 2 makes the user scroll to learn which Mac owns BenQ and which speaker is selected.
`Presentation.swift:statusSections` places an empty Recovery section before monitor
and audio sections. Keep error recovery prominent when active, but make healthy state
compact: both ownership summaries, desktop source and selected speaker first. Preserve
independent observation ages; do not make retained mode values appear live.

Acceptance: the two ownership summaries and selected speaker fit at Largest/minimum
without reducing the chosen font. Long device names wrap/scroll; recovery takes priority
when needed; stale, unknown, away and unmanaged cases remain explicit. No new DDC reads.

### U3 — Align recovery instruction and action (medium)

Step 7 says “Check health, then … Repair audio” while exposing Repair first. Give a
read-only Check health action beside Repair, or revise the guidance to match the actual
safe sequence. Show the immediate reason and retry eligibility before the long last
error. No generic Reset all button, implicit unpause or audio-override cancellation.

Acceptance: ready/degraded/stale/manual/paused/preview cases expose only their valid
requests; eligibility is re-evaluated on click; busy state prevents duplicate submission.
A command acknowledgement and an audible result must remain distinct.

### U4 — Reduce repeated text and improve precise-control discovery (medium)

Steps 3–5 repeat instructions and give secondary information space before common tasks.
Remove the duplicate Displays empty-state explanation. In Audio, show the current
profile preference near the selected output, with other profile preferences grouped
below. Put precise percentage entry beside the confirmed reading; keep read freshness
and explicit Apply. No live drag writes or automatic synchronized brightness.

The percentage slider's accessible value is 50 when the numeric proposal is empty;
this can confuse a screen-reader user who reaches it before the explanation. That is
an accessibility risk, not a confirmed VoiceOver failure. Qualify speech and give the
slider an explicit “no value chosen” context if needed. Invalid 101 retained the last
valid slider position (10), while Apply correctly stayed disabled; label invalid text
as an error rather than suggesting that slider position is an accepted request.

### U5 — Keep release evidence and UI fixtures trustworthy (high engineering priority)

The existing working-tree fixture correction aligns portrait health with portrait
preview choices and supplies the saved-preset estimate. The mismatch demonstrated how
synthetic state can invalidate its own preview. Extract a cohesive demo fixture builder
when next touching this boundary, and check cross-report identity/orientation consistency.
Avoid multiplying hand-written state dictionaries or building a second controller.

`MenuApp.swift` has 955 lines and `display-auto.py` 991; these counts are navigation
signals, not defects. Prefer extracting one affected presenter or fixture module over
an unrelated rewrite. Preserve the authoritative native source inventory and test both
menu and setup builders after an extraction.

Many historical review documents still describe formerly missing features. The current
plan must carry the live priority list; historical evidence should link forward, not
compete as another current roadmap. Guides describe current behavior, logs exact evidence.

## Feature choices informed by other apps

See the [primary-source comparison](research/display-app-comparison-2026-09-21.md)
for licensing, transport limitations and sources. The following are recommendations,
not copied implementation or compatibility promises.

| Feature | Decision |
| --- | --- |
| Guided scale matching, inspired by BetterDisplay | Highest-value product work. Finish the existing workflow; do not reimplement HiDPI or promise native sharpness at every scale. |
| Fast per-monitor controls, inspired by MonitorControl | Improve the existing Controls layout and confirmed value feedback. Global media-key interception is later and optional; explicit targets remain safer across two Macs. |
| Local Shortcuts actions, as offered by Lunar/BetterDisplay | Useful next new capability after UI fixes: status, timed pause/resume, then named preset previews with normal confirmation. Reuse the CLI/controller, no network service. |
| BenQ comfort-settings inspection, informed by Display Pilot and Didact | Research first, initially read-only. Do not claim undocumented multiplexed-register readbacks are confirmed. Fall back to a clear OSD checklist if safe reads cannot be established. |
| Visual layout editor | Defer. Existing read-only topology and saved layouts cover the core use case; an editor needs reversible layout transactions and explicit enrollment scope. |
| Brightness matching | Optional future manual calibration. Same percentages do not mean the same luminance; never label an estimate as measured nits. No new ambient-light loop for a setup with prior pulsing. |
| Virtual displays, PiP, HDR boosting, application-triggered color modes | Defer: substantial platform or automation complexity, weak benefit to the currently accepted desktop. |

Apple's guidance supports larger text, discoverable keyboard operation and focus-state
handling; this review applies those principles to the observed issues rather than
claiming a checklist pass. [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility),
[Focus and selection](https://developer.apple.com/design/human-interface-guidelines/focus-and-selection),
[Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos).

## Reliability work that features must not hide

- Rotation timing is already recorded in phases. Use exact-revision physical evidence
  to distinguish sensor observation, confirmation, layout and readback. Do not lower
  debounce or add polling without a measured bottleneck. One sample cannot establish p95.
- Installer/rollback fixtures cover copy failure, service failure and release-pointer
  interruption. Full multi-file commit interruption and power-loss durability remain
  different, unqualified cases. Retain explicit recovery state before broadening claims.
- Mac B, concurrent controllers, external headset transitions and sleep/wake remain
  unqualified. Mac B testing is deferred; the user does not use sleep. Record those
  boundaries instead of treating a health heartbeat as physical proof.
- Verify exact source/binary agreement before deployment. The audit's synthetic fixture
  build and the installed controller are separate; no installation was performed here.

The [current delivery plan](plans/ui-feature-priority-review-2026-09-21.md) defines
implementation order, tests and rollback. Start with U1, then U2/U3; ship coherent fixes
before adding another feature panel.
